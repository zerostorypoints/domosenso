# SPEC-006: `plants` 0.2.0 — plant entities, water reminder, silent-sensor alert

Status: approved 2026-10-21 by the maintainer, as one batch (draft 2026-10-21).
Source: SPEC-002 §2.3 (row `plants`), plan Task 19; the maintainer's home plants package (read
2026-10-21).

## Goal

0.1.0 describes the sensors only. 0.2.0 renders a managed package: one `plant` entity per plant with
its thresholds, a 24-hour light peak per plant (the current reading is zero every night), a push
when a plant dries out, and a push when a sensor goes silent (Mi Flora reports no battery level
through the proxies, so silence is how a flat cell or a pot out of range shows).

## Devices, integrations

Unchanged from 0.1.0. New core platform used: `statistics`.

## Inputs

Existing, unchanged in name, type and default: `plants`, `plant_defaults`. The item shape stays the
Ramka's `plants` shape, so a home can use one list for both. New, all optional:

| input | type | default | note |
|---|---|---|---|
| `plants[].name` | string | the item's `label` | the plant entity's friendly name (set through `customize`; `plant` has no name option) |
| `plants[].sensors` | `{moisture, conductivity, brightness, temperature}` | `sensor.<plant>_{moisture,conductivity,illuminance,temperature}` | `<plant>` = the object id of `entity` |
| `plants[].min_temperature`, `max_temperature` | number | absent (no temperature check) | also read from `plant_defaults` when there |
| `plants[].check_days` | int | `3` | days over which the brightness peak is judged |
| `notify` | action | — (required) | `notify.mobile_app_alex_phone` |
| `notify_from`, `notify_until` | `HH:MM:SS` | `"08:00:00"`, `"21:00:00"` | a plant drying out outside this window waits for the morning run at `notify_from` |
| `dry_for` | `HH:MM:SS` | `"01:00:00"` | below `min_moisture` this long before the push |
| `silent_hours` | int | `6` | a moisture sensor unavailable this long gives the silent push |

Each threshold: the plant's own value, else `plant_defaults`, else absent.

## Provides (additive-only to the manifest; every id equals the maintainer's home today)

| entity | `unique_id` / automation `id` | stability |
|---|---|---|
| `plant.<plant>` | — (YAML `plant` has none; the id is the key) | stable (as 0.1.0) |
| `sensor.<plant>_illuminance_max_24h` | `<plant>_illuminance_max_24h` | stable |
| `automation.plants_need_water` (alias `Plants need water`) | `plants_water_reminder` | stable |
| `automation.plant_sensor_silent` (alias `Plant sensor silent`) | `plants_sensor_silent` | stable |

The statistics sensor's `name` is `<plant> illuminance max 24h` with the object id, so a fresh
registry derives the same id; `customize` gives it the friendly name `<name> illuminance max 24h`.

Silent automations it carries: both (`loaded_on`).

## Artifacts and layers

- `templates/package.yaml.j2` → `packages/plants.yaml` (managed): `homeassistant.customize`, `plant:`,
  `sensor:` (statistics), the two automations. The water reminder triggers on each plant's own
  `min_moisture` (today's package has one fixed 15 % for all); the messages name the plant by its
  friendly name, as today.
- `translations/*`: `meta.description` updated. No `ui.*` text.
- `README.md`: the brightness threshold is compared with the peak of `check_days`, not the current
  reading; renaming discovered sensors to `sensor.<plant>_*` (or setting `sensors`).

## Compatibility

Additive. In the maintainer's home the local plants package goes. The two automations' configs differ
from today's (per-plant thresholds, inputs for the window, no names of people in descriptions), so
the migration comparison shows `config-differs` for both, reviewed and explained as `config` entries.
