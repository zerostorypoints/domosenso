# SPEC-007: `awnings` 0.2.0 — MQTT covers, sunset retract, wind sensor watch, frame bridge

Status: approved 2026-10-21 by the maintainer, as one batch (draft 2026-10-21).
Source: SPEC-002 §2.3 (row `awnings`) and §2.4, plan Task 19; the maintainer's home awnings package,
its frame bridge (`bridge.py`, `Dockerfile`, how it is run) and its field notes on the wind sensor
(read 2026-10-21).

## Goal

0.1.0 left the covers to the home (`home_provides`), because ESPSomfy-RTS 2.4.6's own discovery is
rejected by Home Assistant. 0.2.0 renders them: one MQTT cover per shade, the wind sensor as an MQTT
binary sensor fed by a frame bridge, a retract at sunset (and after a start between sunset and
sunrise), and a watch that pushes once a day while the wind sensor has not been heard. The frame
bridge ships as a compose service artifact.

## Devices

As 0.1.0, plus a requirement the home provides: an MQTT broker (`kind: mqtt-broker`; a catalog
`mqtt-broker` component is a later candidate, SPEC-002 §2.4). The bridge runs on any Docker host on
the same network as the node.

## Integrations

As 0.1.0 (`mqtt` core, ESPSomfy-RTS firmware 2.4.6 with its HA discovery off). The bridge: Python
3.14 image, `websockets` 15.0.1, `paho-mqtt` 2.1.0 (as the home runs it).

## Inputs

Existing, unchanged: `covers` (`list[{name, shade_id}]`), `mqtt_root_topic` (`espsomfy`),
`wind_sensor` (entity id, default `null`: with a value the component now declares that sensor under
that id; without one, no wind entities and no wind automations). New:

| input | type | default | note |
|---|---|---|---|
| `node_id` | string | — (required) | prefix of every `unique_id` and the device identifier, e.g. `espsomfy_a1b2c3` |
| `covers[].entity_id` | entity_id | from `name` | pins the cover's id (`default_entity_id`) |
| `node` | `{name?, model?, area?, url?}` | name `ESPSomfy RTS`, manufacturer `rstrouse` | device info of the node |
| `wind_name` | string | `Awnings wind` | |
| `wind_off_delay` | int s | `120` | the all-clear frame is often lost |
| `wind_last_heard` | `{id, name}` | `{id: awnings_wind_last_heard, name: Awnings wind last heard}` | the `input_datetime` the heard automation writes |
| `wind_silent_hours` | int | `72` | |
| `wind_check_time` | `HH:MM:SS` | `"10:00:00"` | the daily check |
| `retract_at_sunset` | bool | `true` | |
| `notify` | action | — (required with `wind_sensor`) | |

Silent automations it carries: `awnings_wind_sensor_heard` (`loaded_on`, `triggered_within: 48`) and
`awnings_wind_sensor_silent` (`loaded_on`). After a restart the wind sensor is `unknown` until the
next frame (`after_restart: unknown`).

## Artifacts and layers

- `templates/package.yaml.j2` → `packages/awnings.yaml` (managed): `mqtt:` binary sensor and covers,
  the three automations, the `input_datetime`. Same structure and logic as the home's package (state
  from the position alone, the retained-position reason, one radio command every 3 s).
- `services/frame-bridge/` (managed, deployed in phase 5, not by the cut-over): `bridge.py`,
  `Dockerfile`, `compose.yaml` (host network, `restart: always`, `/data` volume, `env_file`) and
  `bridge.env.example`. Listed in `artifacts.services` by path. Changes against the home's bridge:
  the root topic from `ROOT_TOPIC` (default `espsomfy`) instead of fixed; `NODE_WS` and `MQTT_HOST`
  required (no addresses in the catalog); `WIND_SENSOR` optional (no wind topic without it);
  `MQTT_PORT` (default 1883). With the home's values it publishes exactly what it does today.
- `artifacts.home_provides` goes (the component renders the package now).
- `translations/*`: `meta.description` updated. No `ui.*` text.
- `README.md`: the discovery bug, the wind sensor's report pattern (gaps up to 36 h, none heard
  10:00-14:00), why the bridge exists (the node publishes the wind flag only on change and retains
  positions only at boot), the bridge's websocket pings.

## Compatibility

Additive for homes: 0.1.0 rendered nothing. `home_provides` was a catalog-side pointer, no home reads
it. In the maintainer's home the local awnings package goes; the running bridge container is not
replaced at the cut-over (SPEC-002 §2.4); its source in the home repository is superseded by the
catalog's in phase 5. Automation configs differ from today's in description and message text (no
names of people), so the comparison shows `config-differs` for the one automation with a notify
(`awnings_wind_sensor_silent`; found in Step 2: the other two render equal to the home's), reviewed
and explained as a `config` entry.

## Tests

`catalog_check --strict` (service paths exist); `tools/ha-check.sh awnings` → `fresh: 0 errors` with
demo-home inputs (two awnings, a wind sensor); pytest for the bridge's frame parsing, burst filter
and topic building (no network); `docker compose config` of `compose.yaml` **(only if docker compose
is available; inference that `ha-check`'s Docker host has it)**; Task 19 staging comparison (its
throwaway MQTT broker loads the `mqtt:` entities).

## Out of scope
