# SPEC-003: `backup` 0.1.0 — nightly backups with rolling retention

Status: approved 2026-10-21 by the maintainer, as one batch (draft 2026-10-21).
Source: SPEC-002 §2.3 (row `backup`), plan `docs/2026-10-21-domosenso-whole-home-plan.md` Task 19;
the maintainer's home package for backups and its retention script (read 2026-10-21; household
values are in that home's inventory, not here).

## Goal

A home on a Container install gets a full Home Assistant backup every night, a catch-up backup when
Home Assistant starts and the newest backup is too old, a retention that keeps the newest few plus
one per recent week, three sensors that show whether backups are happening, and a push when they
stop. Today's behaviour of the maintainer's home, with the times, counts and recipient as inputs.

## Devices

None. Backups go to `/config/backups` (the `backup` integration's local agent) on the host's disk.

## Integrations

All core, no setup: `backup` (`backup.create`), `command_line` (the sensors), `shell_command` (the
retention script). Home Assistant's own automatic-backup schedule stays off; this component replaces
it because the core retention has no "one per week" rule.

`host.installs: [container]` only: the sensors read `/config/backups`, which is where a Container
install keeps local backups; on HAOS they live in `/backup`. **(inference: HAOS path; not tried)**

## Inputs

| input | type | default | example |
|---|---|---|---|
| `time` | `HH:MM:SS` | `"03:30:00"` | |
| `catch_up_hours` | int | `20` | a start backs up when the newest backup is older than this |
| `keep_daily` | int | `7` | newest archives kept |
| `keep_weekly` | int | `4` | plus the newest archive of each of the last N ISO weeks |
| `stale_hours` | int | `30` | the alert fires after one more hour above this |
| `notify` | action | — (required) | `notify.mobile_app_alex_phone` |

## Provides (all new, from the managed package)

| entity | `unique_id` / automation `id` | stability |
|---|---|---|
| `sensor.newest_backup_age` (h, 9999 when there is none) | `backup_newest_age_hours` | stable |
| `sensor.backup_count` | `backup_count` | stable |
| `sensor.backup_folder_size` (MB) | `backup_folder_size` | stable |
| `shell_command.prune_old_backups` | — | stable |
| `automation.nightly_home_assistant_backup` | `nightly_home_assistant_backup` | stable |
| `automation.alert_when_backups_stop` | `backup_stale_alert` | stable |

These are exactly the ids and `unique_id`s the maintainer's home has today. Command-line sensors take
no attributes, so they carry no `component:` marker (the marker rule is for template entities).

Silent automations it carries (for a home's `silent.yaml`): `nightly_home_assistant_backup`
(`loaded_on`, `triggered_within: 25`, `entity_fresh: sensor.newest_backup_age` under 30 h) and
`alert_when_backups_stop` (`loaded_on`).

Consumes: nothing.

## Artifacts and layers

- `templates/package.yaml.j2` → `packages/backup.yaml` (managed): the three sensors, the shell
  command, the two automations. Same structure as the home's package; text in English (packages
  render in `en`), no names of people or devices in descriptions or messages.
- `shell/prune_backups.py` → `/config/shell/prune_backups.py` (managed): the home's script with
  `--keep-daily N --keep-weekly N` arguments instead of constants (the shell command passes the
  inputs) and `--dry-run` as today.
- `translations/{en,de,pl}.json`: `meta.description`. No `ui.*` text (no dashboard).
- `README.md` field notes: the archive is not encrypted and holds the auth store and integration
  credentials, so any copy off the host needs client-side encryption; restore from onboarding or
  Settings → System → Backups.

## Compatibility

New component, nothing to migrate in the catalog. In the maintainer's home the local `backup.yaml`
and `shell/prune_backups.py` are replaced by the managed ones (plan Task 19 Step 3). Automation
configs will differ from today's in their description and message text (no names of people), so the
migration comparison shows `config-differs` for the two automations; each is reviewed and explained
as a `config` entry. Entity ids and `unique_id`s do not change.

## Tests

## Out of scope
