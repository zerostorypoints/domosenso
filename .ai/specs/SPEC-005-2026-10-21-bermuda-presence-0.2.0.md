# SPEC-005: `bermuda-presence` 0.2.0 — the blueprints become the live path

Status: approved 2026-10-21 by the maintainer, as one batch (draft 2026-10-21).
Source: SPEC-002 §2.3 (row `bermuda-presence`), plan Task 19; `docs/pilot-bermuda-presence.md`; the
maintainer's home presence package (generated by its floor-plan tool) and its proxy-offline package
(read 2026-10-21).

## Goal

The pilot (0.1.0) proved the two blueprints and wrote the demo home's instance file by hand. 0.2.0
renders that instance file from the inputs, so `domosenso add bermuda-presence` writes it once into a
home, and a home's own generated presence package and proxy-offline package can go.

## Devices, integrations

Unchanged from 0.1.0. ESPHome packages unchanged (thin device files are phase 5, SPEC-002 decision 3).

## Inputs

Unchanged: `rooms`, `phones`, `tablets`, `proxies`, `offline_notify`, `minutes`. New, optional:

| input | type | default | note |
|---|---|---|---|
| `room_ids` | `map[area_name, slug]` | `{}` | the id part for an area whose name does not slugify to the home's current id |

The id part of a room is otherwise the area name slugified as Home Assistant does it: lower case,
letters with diacritics to their base letter (`ó`→`o`, `ś`→`s`, `ä`→`a`, `ß`→`ss`), every other run
of non-alphanumerics to `_`. `Kids' room` → `kids_room`.

## Provides (unchanged ids; every id equals the maintainer's home today)

| entity | `unique_id` / automation `id` | stability |
|---|---|---|
| `sensor.presence_<room id>` (name `Presence <area>`) | `presence_<room id>` | stable (as 0.1.0) |
| `automation.ble_proxy_offline` (alias `BLE proxy offline`) | `ble_proxy_offline_alert` | additive-only (as 0.1.0) |

The proxy-offline automation triggers on `sensor.<area slug>_ble_proxy_<room>_wi_fi_signal` of
every entry in `proxies` (the ESPHome entity the manifest already provides). Rooms come from `rooms`;
a room without a proxy still gets its sensor (Bermuda then never reports it, the state stays `-`).

Silent automation it carries: `ble_proxy_offline` (`loaded_on`).

## Artifacts and layers

- `ha/blueprints/template/domosenso/presence_room.yaml`, `ha/blueprints/automation/domosenso/ble_proxy_offline.yaml`
  → `blueprints/*/domosenso/` (managed), unchanged.
- New `templates/instance/packages/bermuda_presence.yaml.j2` → `packages/bermuda_presence.yaml`
  (instance: written once by `domosenso add`, no stamp, the home's from then on): one
  `use_blueprint` template sensor per room with `name` and `unique_id`, and the automation instance
  with `id: ble_proxy_offline_alert`.
- `artifacts.ha_instance` stays `examples/demo-home/ha/packages/bermuda_presence.yaml` (what
  `ha-check` loads). That file becomes exactly what the instance template renders from the demo
  inputs; a new pytest (`tests/test_instance_templates.py`) renders every component's
  `templates/instance/` with its demo inputs and fails when the result differs from the committed
  `ha_instance` file (parsed YAML), so the check covers the template without changing `ha-check.sh`.
- `translations/*`: no change beyond what exists (no `ui.*` text).

## Compatibility

Additive: a new artifact kind for this component, one new optional input, no id changes. A home that
copied the pilot's instance by hand keeps its file (instance layer). In the maintainer's home the
generated presence package and the proxy-offline package go; the floor-plan tool stops writing the
presence package and its phone / tablet / room tables move to the component's inputs (plan Task 19,
home side). The automation's config becomes a blueprint instance, so the migration comparison shows
`config-differs` for `automation.ble_proxy_offline`, reviewed and explained as a `config` entry. The
presence sensors gain the `component` and `area` attributes (the blueprint's marker), which the
comparison does not read.
