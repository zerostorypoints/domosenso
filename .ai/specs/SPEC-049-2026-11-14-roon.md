# SPEC-049 — Roon

**Status:** approved 2026-11-14

**Source:** the maintainer's home asked for Roon with full support (2026-11-14). It runs a Roon Core
(ROCK on an Intel NUC, Roon Server 2.74, build 1719) and several Roon Ready amplifiers and
streamers. Home Assistant has no Roon integration yet. The integration's code was read at the
`2026.9.2` tag of `home-assistant/core`.

## Goal

A home with a Roon Core gets:

- one Home Assistant player per Roon zone, through the core `roon` integration. The Ramka's
  music view and the audio chain can show and control these players.
- Roon's volume buttons turning the volume of an amplifier that Roon cannot control itself. These
  are the zones whose output has fixed volume, for example a DAC feeding an amplifier with an IR or
  network remote.
- field notes: setup, zone naming, play paths, transfer, grouping, and what each player
  attribute means.

Placement test:

1. **Home Assistant already offers the players.** The core `roon` integration does it, so the
   catalog writes no integration and no player template.
2. **A second home needs the rest.** Two things are missing from Home Assistant:
   - the volume bridge. The integration only fires `event.<zone>_roon_volume` events, and every
     home would otherwise write the same automation by hand;
   - the Roon Core as a device the catalog recognizes.

   Both go into a small component.
3. **This home only:** which zones feed which amplifier, and the audio-chain source file. These
   stay in the home's local layer.

## Devices

- **Required:** a Roon Core on the home network: ROCK, Nucleus, or Roon Server on a computer or
  NAS. New kind `roon-core`, matched by `entry: roon` (one config entry per Core), and new device
  `roon-core` without a device rule. The hub device (`Roonlabs`) and the zones (`RoonLabs`) differ
  only in case, and match rules ignore case.
- **Zones:** any Roon output. They match the existing `network-audio-player` kind (`maybe`), as
  every `media_player` does.
- **Tested:** one ROCK on Roon Server 2.74 (1719) with Roon Ready endpoints. Assumed: Nucleus and
  Roon Server on other hosts behave the same, because the extension API is the same.

## Integrations

| name | source | tested | human setup |
|---|---|---|---|
| `roon` | core (`roonapi==0.1.6`, local push) | HA 2026.9.2 | Settings → Devices & services → Add → Roon. The Core is discovered, or its address is entered by hand (needed when HA's container has no host networking, because discovery uses multicast). Then in the Roon app: Settings → Extensions → Enable "Home Assistant". Assign an area to each zone. |
| for each bridged zone | Roon app | — | Zone → Device setup → Volume control → "Home Assistant: \<zone\> roon volume" |

The following was verified in `media_player.py` and `event.py` at 2026.9.2:

- **One `media_player` per output.** Its name is Roon's display name and its `unique_id` is the
  output's `dev_id`.
- **Features:** browse, grouping (join and unjoin, limited to `can_group_with_output_ids`), pause,
  stop, previous, next, repeat, shuffle, seek, on and off, mute, play, `play_media`.
  - `volume_step` only when the output has volume.
  - `volume_set` only when that volume is absolute, not incremental.
  - A fixed-volume zone has neither, so it does not meet the Ramka's `media_player_contract`
    (`volume_set` is required).
- **State:**
  - `off` when the output's source control supports standby and reads `standby` or `deselected`.
  - Otherwise it follows Roon: `playing` (which includes `loading`), `paused`, or `idle`.
  - A removed zone reads unavailable and `off`.
- **Now playing:** `media_title`, `media_artist` and `media_album_name` come from Roon's three
  lines, plus position, duration and an image URL from the Core. There is no `source` or `app_name`.
- **`roon.transfer`:** the target is the source zone and `transfer_id` is the destination.
- **`event.<zone>_roon_volume`:** one for every zone, device class `button`, event types
  `volume_up`, `volume_down` and `mute_toggle`. It registers an incremental volume control named
  "\<zone\> roon volume" in Roon. Every press is one event, and the size of Roon's step is not
  passed on.

## Inputs

| key | type | default | example |
|---|---|---|---|
| `volume_bridges` | list | `[]` | see below |
| `volume_bridges[].event` | entity_id (`event.*_roon_volume`) | — | `event.study_dac_roon_volume` |
| `volume_bridges[].amplifier` | entity_id (`media_player`) | — | `media_player.study_amplifier` |
| `volume_bridges[].steps` | int 1–5 | `1` | `2`: how many `volume_up` or `volume_down` calls each press makes |
| `volume_bridges[].mute` | bool | `true` | `mute_toggle` calls `volume_mute` with the opposite of `is_volume_muted` |

`render` fails, and gives the reason, when:

- an `event` does not end in `_roon_volume`;
- an `amplifier` is not a `media_player`;
- two bridges name the same `event`.

## Provides

| entity | stability | note |
|---|---|---|
| `automation.roon_volume_<zone>` | stable | one for each bridge, `mode: queued`, `max: 20`; `<zone>` is the event id without `event.` and `_roon_volume` |

Upstream entities, owned by the `roon` integration. They are listed so that consumers can bind to
them:

- `media_player.<zone>`
- `event.<zone>_roon_volume`

**Consumes:** the amplifier's `media_player` (`volume_up`, `volume_down`, `volume_mute`).

## Ramka

No change in this spec. A Roon zone with absolute volume meets the contract and can be the
Ramka's `media_player`, or it can feed a home's own virtual player. The README says which zones
qualify.

The now-playing card has no seek, shuffle or repeat controls. Adding them would be a Ramka
change for every player and gets its own spec if it is wanted.

## Compatibility

This is a new component at 0.1.0, so no existing home has to change anything. There is no bridge
and no `UPGRADE.md` entry.

## Tests

- `catalog_check`: the manifest, kind, device and translations.
- pytest renders:
  - no bridge (empty package);
  - one bridge with `steps: 2` and `mute: false`;
  - each refusal listed under Inputs.
- `ha-check` on the rendered package.
- Staging or the maintainer's production, after a go-ahead:
  - the integration is authorized;
  - a fixed-volume zone is bridged to an amplifier;
  - a + press in the Roon app moves the amplifier by one step, and a mute press toggles it.

## Out of scope

- A new Roon integration, or anything that uses Roon's protocol directly. The extension API is
  enough, and Roon's EULA forbids decompiling.
- Library or radio shortcuts on the Ramka, and presence automations that start a playlist. The
  README gives example `play_media` paths (`Library/Artists/<artist>/<album>`,
  `My Live Radio/<station>`) for homes to use in their own automations.
- Upgrading RoonOS. It has no effect on the integration.
